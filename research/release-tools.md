# Release tools for redact: release-please, release-plz, dist

Research for [#20](https://github.com/Drewtopia/redact/issues/20). Checked 2026-11-14 against release-please v17.11.2, release-plz 0.4.3 and dist 0.34.0.

## Answer

**release-please** fits best. Of the three, it is the only one that bumps `claude-plugin/.claude-plugin/plugin.json` alongside `Cargo.toml` without custom code. It also supports draft releases directly. Keep the current build jobs in `.github/workflows/release.yml` and drop its `create-release` job, because release-please creates the draft.

dist doesn't compete with the other two. Its own docs say it doesn't pick versions, write changelogs or create tags ([cargo-release guide](https://axodotdev.github.io/cargo-dist/book/workspaces/cargo-release-guide.html): "dist intentionally doesn't handle these steps of cutting a release for you"). It could later replace the build layer, which is today's `release.yml`. It can't replace a versioning tool.

The setup has two layers:

1. **Versioner.** It reads Conventional Commits, opens a release PR that bumps the versions and `CHANGELOG.md`, and tags the release when that PR is merged. The candidates are release-please and release-plz.
2. **Builder.** It runs on the tag, builds the six targets, uploads them, and publishes. Today that is `release.yml` (taiki-e actions). dist is the alternative.

## Comparison

| | release-please | release-plz | dist |
| :- | :- | :- | :- |
| **Next version from Conventional Commits** | `fix:` → patch, `feat:` → minor, `!` → major ([README](https://github.com/googleapis/release-please/blob/main/README.md)). **Pre-1.0 caution:** `bump-minor-pre-major` defaults to false ([`default.ts`](https://github.com/googleapis/release-please/blob/main/src/versioning-strategies/default.ts) sets it only when `=== true`), so a `feat!:` on 0.2.0 jumps to 1.0.0 unless you set it. `bump-patch-for-minor-pre-major` makes `feat:` a patch bump below 1.0 ([config schema](https://github.com/googleapis/release-please/blob/main/schemas/config.json)). `Release-As: x.y.z` in a commit body forces a version. | Uses the [`next_version`](https://docs.rs/next_version/latest/next_version/) crate ([FAQ](https://release-plz.dev/docs/faq)). On 0.x: `feat` → patch, breaking → minor, and on 0.0.x always patch. `features_always_increment_minor` makes `feat` a minor bump on 0.x ([config](https://release-plz.dev/docs/config)). cargo-semver-checks can force a major bump, but only "for packages containing a library" ([semver-check](https://release-plz.dev/docs/semver-check)). redact is binary-only, so that check never runs. | Doesn't decide versions. "All dist cares about is that a tagged commit eventually ends up in your repo" ([guide](https://axodotdev.github.io/cargo-dist/book/workspaces/cargo-release-guide.html)). |
| **CHANGELOG.md** | Written from commit messages in the release PR, grouped by commit type with links to PRs and commits ([customizing](https://github.com/googleapis/release-please/blob/main/docs/customizing.md)). Sections are configurable with `changelog-sections`. A PR body can correct notes with `BEGIN_COMMIT_OVERRIDE` (squash-merge only). | Written in the release PR by git-cliff, used as a library ([changelog](https://release-plz.dev/docs/changelog)). Grouping uses `[changelog] commit_parsers` ([config](https://release-plz.dev/docs/config)). | Doesn't write one. It reads `CHANGELOG.md` to fill in the GitHub release title and body, and auto-includes it in archives ([config](https://axodotdev.github.io/cargo-dist/book/reference/config.html)). |
| **Tag and build trigger** | When you merge the release PR, it tags the commit and creates the GitHub release ([README](https://github.com/googleapis/release-please/blob/main/README.md)). Set `include-component-in-tag: false` to get plain `v0.3.0` ([manifest-releaser](https://github.com/googleapis/release-please/blob/main/docs/manifest-releaser.md)). The action exposes `release_created` and `tag_name` for jobs later in the same workflow ([action README](https://github.com/googleapis/release-please-action/blob/main/README.md)). | `release-plz release` creates the tag, runs `cargo publish` and creates the GitHub release ([release](https://release-plz.dev/docs/usage/release)). It doesn't build binaries. It suggests a separate job "on the "tag" or "release" events" using upload-rust-binary-action or dist ([releasing binaries](https://release-plz.dev/docs/extra/releasing-binaries)). | Its generated workflow runs on a tag push matching `**[0-9]+.[0-9]+.[0-9]+*`, or on `workflow_dispatch` with `dispatch-releases = true` ([template](https://github.com/axodotdev/cargo-dist/blob/main/cargo-dist/templates/ci/github/release.yml.j2), [config](https://axodotdev.github.io/cargo-dist/book/reference/config.html)). |
| **Second versioned file (`plugin.json`)** | Built in. `extra-files` with `"type": "json", "path": "claude-plugin/.claude-plugin/plugin.json", "jsonpath": "$.version"` bumps the version in the same release PR ([customizing](https://github.com/googleapis/release-please/blob/main/docs/customizing.md)). | No option for non-Cargo files ([config](https://release-plz.dev/docs/config) has none, and the FAQ doesn't cover it). `version_group` only links Cargo packages. You would have to add a job that edits `plugin.json` and pushes to the release PR branch. | Not applicable, since it versions nothing. |
| **Draft releases** | `draft: true` creates the release as a draft. Also set `force-tag-creation: true`: "GitHub does not create a Git tag for draft releases until they are published," and without the tag release-please can't find the previous release and writes a wrong changelog ([schema](https://github.com/googleapis/release-please/blob/main/schemas/config.json), [manifest-releaser](https://github.com/googleapis/release-please/blob/main/docs/manifest-releaser.md)). | `git_release_draft = true` ([config](https://release-plz.dev/docs/config)). The docs say nothing on whether the tag exists while the release is still a draft. | The default (`create-release = true`) creates the release only after every build has finished, with one `gh release create … artifacts/*` call ([`github.rs`](https://github.com/axodotdev/cargo-dist/blob/main/cargo-dist/src/backend/ci/github.rs): "When creating release, upload artifacts transactionally"). That removes the half-uploaded window that the draft step guards against today. With `create-release = false` it expects a draft for the tag to exist already, then uploads to it and undrafts it ([config](https://axodotdev.github.io/cargo-dist/book/reference/config.html)). That setting suits a release-please draft. |
| **Fit with no crates.io** | `rust` release type updates `Cargo.toml` and `Cargo.lock` ([`rust.ts`](https://github.com/googleapis/release-please/blob/main/src/strategies/rust.ts)), and it "does not handle publication to package managers" ([README](https://github.com/googleapis/release-please/blob/main/README.md)). No change needed. | By default it skips `publish = false` packages ([FAQ](https://release-plz.dev/docs/faq)) and compares against the cargo registry, where `redact` is someone else's crate. You need `git_only = true`, which takes versions from git tags and tags `publish = false` packages anyway ([config](https://release-plz.dev/docs/config)). The docs don't confirm the tag name in that mode, so set `git_tag_name = "v{{ version }}"` to match today's trigger. | Doesn't publish to crates.io. |

## The catch for both versioners: the token

A tag or release created with the default `GITHUB_TOKEN` doesn't start another workflow run. GitHub: "events triggered by the `GITHUB_TOKEN` will not create a new workflow run," except `workflow_dispatch` and `repository_dispatch` ([GitHub docs](https://docs.github.com/en/actions/concepts/security/github_token)). release-please and release-plz both repeat this ([action README](https://github.com/googleapis/release-please-action/blob/main/README.md), [release-plz token](https://release-plz.dev/docs/github/token)). As a result, a tag that release-please creates won't start today's `on: push: tags` workflow. There are three ways around it:

1. **Same workflow.** Make `release.yml` callable (`on: workflow_call`), and call it from the release-please workflow with `if: needs.release-please.outputs.release_created`. No secret is needed. This is the documented pattern in the release-please action README.
2. **Dispatch.** Run `gh workflow run release.yml -f tag=…` after release-please finishes. `workflow_dispatch` is exempt from the token rule. dist has this mode built in (`dispatch-releases = true`).
3. **A PAT or GitHub App token** for release-please. The tag push then triggers `release.yml` as it does today. This option needs a secret, and the secret has to be rotated.

Option 1 is the smallest change and needs no secret.

## What adopting release-please changes in this repo

- Add `release-please-config.json` with these settings: `release-type: rust`, `include-component-in-tag: false`, `bump-minor-pre-major: true`, `draft: true`, `force-tag-creation: true`, and the `plugin.json` entry in `extra-files`. Add `.release-please-manifest.json` containing `{".": "0.2.0"}`. Tags `v0.1.0` and `v0.2.0` and their releases already exist, so release-please can find the previous release without `bootstrap-sha`.
- In `release.yml`, delete the `create-release` job, because release-please now creates the draft. The tag-matches-`Cargo.toml` check moves to the `upload-assets` job or is dropped, since release-please writes both. `upload-assets` and `publish-release` stay as they are.
- Version bumps come from commit messages. Recent squash merges such as #14 and #15 follow Conventional Commits, but #10 and #11 landed as `Merge pull request …` commits, which release-please doesn't count. Squash-merging every PR keeps the history readable to it.

## Keeping the mod's version: lockstep or delete

Claude Code offers a native alternative to bumping `plugin.json`: leave `version` out. "Omit `version`: users track your commits instead" ([host a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md)). For a plugin inside a git-hosted marketplace, the version becomes the commit SHA ([loading](https://code.claude.com/docs/en/plugins/loading.md)). The cost is that the mod on `main` could call binary behaviour that isn't released yet, so a user who updates the mod before the binary breaks. Keeping `plugin.json` in lockstep with `Cargo.toml` through `extra-files` means a mod version always names a binary release that exists. That fits redact, where the mod is a thin wrapper over the binary.

`claude plugin tag` creates `<name>--v<version>` tags for plugin dependency resolution ([CLI reference](https://code.claude.com/docs/en/plugins/cli-reference.md)). redact's mod has no dependents, so it doesn't need them. dist's default tag glob would also match such a tag, which matters only if someone adopts the command later.

## If dist replaces the build layer later

These costs apply whichever versioner is chosen:

- Archive names drop the version (for example `redact-x86_64-unknown-linux-musl.tar.xz`, and `.zip` on Windows; [config](https://axodotdev.github.io/cargo-dist/book/reference/config.html)). Today's assets are `redact-v0.2.0-<target>`. The workflow comment says mise matches on the target triple, but that needs checking before the switch.
- dist generates and owns `release.yml` (`dist init`, [quickstart](https://axodotdev.github.io/cargo-dist/book/quickstart/rust.html)). Hand edits go in its config, not in the YAML.
- Auto-includes cover README, LICENSE and CHANGELOG. `LICENSE-THIRD-PARTY` would need `include`.
- In return: installers, `.sha256` files by default, all six targets supported, including both musl targets and `aarch64-pc-windows-msvc` ([config](https://axodotdev.github.io/cargo-dist/book/reference/config.html)), and a release that appears only once every file is attached.
