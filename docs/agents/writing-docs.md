# Writing docs pages

The docs site is VitePress, built from `docs/` and published to GitHub Pages under `/redact/` on every push to `main`. `docs/agents/` is excluded from the build. The reader is someone deciding whether redact can hide what they are about to paste into an AI, and then doing it. Each page answers one question for that reader and stops.

## When to act

A PR that changes `src/`, `packs/` or `claude-plugin/` changes a page under `docs/` or `README.md` too (CI checks), or carries the `no-docs` label with a reason in the PR body. Find the page by what the reader would see change:

| The change | The page |
| :- | :- |
| A pack's rules or description | Run `REDACT_BLESS=1 cargo test`; it rewrites `docs/packs/<pack>.md` |
| A new or removed pack | The bless run, plus its row in the table in `docs/packs/index.md` (in load order) and its entry in the sidebar in `docs/.vitepress/config.mts` |
| A CLI flag, subcommand or help text | Run `REDACT_BLESS=1 cargo test`; it rewrites `docs/reference/cli.md` |
| A config key or its behaviour | `docs/reference/config.md`, and the guide page that uses the key |
| A tool redact works with | Its page under `docs/integrations/`, and `docs/integrations/index.md` |
| Something redact now misses, or stops missing | `docs/reference/limits.md` |

A page that starts with `<!-- Generated by ... -->` is generated. Change its source in the code or the pack TOML and bless it; a hand edit fails the test.

A new page, a rename or a removal also updates the sidebar and nav in `docs/.vitepress/config.mts` and every link that pointed at the old path. A moved page leaves a stub at its old path, so published links keep working: copy the frontmatter of `docs/guide/agents.md` (a refresh to the new URL, `search: false`) and a `# Moved` line that links to the new page. Check with `npm run build` in `docs/`: VitePress fails the build on a dead link, and the `docs-build` CI job runs the same build on every PR.

## The four sections

Each section of the site holds one kind of page. Write a new page as the kind its section holds.

| Section | Kind | The page |
| :- | :- | :- |
| `guide/` | How-to | One task, from the config the reader writes to the output they get. |
| `integrations/` | How-to, per tool | One tool: install, then each way that tool leaks something, then the fix. |
| `packs/` | Reference | Generated rule tables. `index.md` and `writing.md` are hand-written. |
| `reference/` | Reference | Every key, flag or limit, complete enough to look up without reading code. |

Every page has one H1, the page title, matching its sidebar text. Under it, one short paragraph says what leaks and what this page does about it. The H2s that follow name what the reader does or gets ("Hide a project's `[env]`", "Leave a value visible"), not the mechanism.

## Examples are public

Every example on the site is published, so every value in one is invented: `Acme`, `ACME_*`, `example.com`, `api.example.com`. A real name, host, tenant or token never goes in, including your own. Output examples show placeholders in redact's real format, such as `[PERSON-9e6bf2c0]`, so the reader learns what to expect.

Show an example as the config or command, then what comes out. A `toml` block starts with a comment naming its file, as in `# ~/.config/redact/config.toml`.

## Voice

- Plain and short. Second person, present tense: "redact hides", "Name the variables".
- Say what redact does, then why the reader cares. Leave out how the scanner works; that lives once, in `reference/how-it-works.md`.
- State what redact misses next to what it hides. The site's promise is honesty about gaps, so an overclaim is a bug.
- Callouts are VitePress containers (`::: warning Title`), kept for what loses the reader data or leaks a secret.

## Links

Links between pages are relative and drop `.md`: `[fnox](../integrations/fnox)`. VitePress adds the `/redact/` base and the clean URL. A link out of the site is a full URL. A link to a file in the repo is its full `https://github.com/Drewtopia/redact/blob/main/...` URL, since the page is read on the site, not in the repo.

## The changelog

`CHANGELOG.md` is written by release-please, never by hand. Its lines are the titles of squash-merged PRs, so the PR title is the reader's changelog entry. Which types bump the version and reach the changelog, and what counts as breaking, are in "Versions and releases" in `CONTRIBUTING.md`.

- Write the title as what changed for the reader, in the site's voice: `fix(scan): hide passwords in quoted --password flags`, not `fix(scan): handle quotes in flag regex`.
- A PR that is only docs is `docs:` and stays out of the changelog. A `feat:` or `fix:` that also updates its page stays one PR with one title.
- A breaking change (`!`) also updates every page that shows the old behaviour, and the page says what to change: the old key, flag or rule id beside the new one.

## Done when

- Every change in the PR that a reader would see has its page updated, or the PR has `no-docs` with a reason.
- `REDACT_BLESS=1 cargo test` has run if a pack or the CLI changed, and `cargo test` passes.
- `npm run build` in `docs/` passes, and the sidebar lists every page.
- Every example value is invented.
- Each page opens with what leaks, and each H2 names what the reader does or gets.
- The PR title reads as a changelog line for the reader, and a breaking change's pages name the old form beside the new.
